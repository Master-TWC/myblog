## 一、这次要做什么

实验二是「数据看板的设计与实现」，技术栈限定 **Streamlit + Pandas + Plotly**，业务场景是电商销售数据（2023-01 ~ 2024-12 的订单明细），要求从业务问题出发，做一个能真正回答问题的看板，而不是把图表堆一页。

任务分三档：

| 档位 | 内容 | 本工程 |
|---|---|---|
| 基础任务 1~5 | 需求与版面设计、数据准备、图表设计、交互与样式、数据验证 | 全部完成 |

最终成品是两个页签：**📌 基础看板（任务 1~5）** 和 **🚀 进阶分析（进阶 1~3 + 扩展 2/4）**，共用左侧一套 6 类筛选器。

## 二、数据：先造脏数据，再洗干净

数据是 `generate_data.py` 随机生成的，但**故意注入了 10 类脏数据**，否则清洗这一步就成了走过场：

| 脏数据类型 | 数量 | 清洗方式 |
|---|---|---|
| 完全重复的记录 | 15 | 按订单编号去重 |
| 关键字段空值 | 12 | 无法补救的直接删除 |
| 负金额 / 零金额 | 8 | 删除，并重算销售额 |
| 数量 = 999 的极端值 | 6 | 业务规则 ≤ 30 + 99.9 分位双阈值 |
| 单价 = 999999 的极端值 | 4 | 同上，按分位数剔除 |
| 折扣率越界（>1 或 <0） | 5 | 截断到 [0, 1] |
| 销售额与「单价×数量×折扣」不一致 | 6 | 统一重算，以公式为准 |
| 日期格式混乱（`2024/1/5`、`2024.01.05`…） | 6 | 分隔符归一后再 `to_datetime(errors="coerce")` |
| 首尾空格 / 全角空格 | 14 | `str.strip()` + 全角空格替换 |
| 客户评分越界（>5 或 <0） | 5 | 截断到 [0, 5] |

清洗前后的对比：**5,115 行 → 5,060 行**，24 个月，0 空值。

![数据清洗流水线](/myblog/images/lab2/08-clean-pipeline.png)

*图 1：12 步清洗流水线——从原始 CSV 到分析用宽表*

有个坑值得单独说：**极端值不能用单一规则判断**。如果只按「数量 ≤ 30」过滤，会误杀大客户的批量订单；如果只按 99.9 分位裁剪，又会漏掉那些刚好卡在分位线下的假数据。最后用的是双阈值：先按业务规则卡上限，再用分位数兜底，并把每一步删了多少行写进 `清洗报告.txt`。

另外，销售额统一由 `单价 × 数量 × (1 − 折扣率)` 重算，而不是直接用表里的值——因为那 6 条口径不一致的记录证明，原始字段并不可信。

## 三、版面：四模块 + 一套配色

版面按「总—分—细」组织成四个区域：

1. **数据概览区**：5 张 KPI 卡（销售额、订单量、客单价、销售件数、客户评分），每张都带同比；
2. **维度统计区**：品类柱状、品类环形、渠道条形、地区柱状，四个维度并排看「谁贡献更大」；
3. **趋势分析区**：2023 vs 2024 双线月度折线 + 四张季度卡；
4. **明细数据区**：品类汇总表 + 订单明细表（默认展示最新 300 条），底部带 CSV 导出。

配色是统一的一套：主色 `#2F6BFF`、辅助 `#00C2A8`、强调 `#FF8A3D`，配上 `#7C5CFF / #F2545B / #FFC93C`，背景 `#F4F6FB`、描边 `#E4EAF6`、文字 `#1B2A4A / #7A88A8`。所有卡片统一 14px 圆角、1px 描边、KPI 卡顶部 3px 主色描边，字体统一微软雅黑。

## 四、几个关键实现

### 4.1 图表样式统一

十几个图如果各写各的 `layout`，很快就会「颜色不一致、标题大小不一致、边距不一致」。所以抽了一个 `base_layout()`，所有图共用背景色、字体、边距、图例位置和 hover 模板；金额类坐标轴统一换成「万元」，否则 `500000` 这种数字会把坐标轴挤爆。

```python
def base_layout(fig, height=330, legend=True, x_title=None, y_title=None):
    fig.update_layout(
        height=height, paper_bgcolor="rgba(0,0,0,0)", plot_bgcolor="rgba(0,0,0,0)",
        margin=dict(l=10, r=10, t=36, b=10), hovermode="x unified",
        font=dict(family="Microsoft YaHei", size=12, color="#1B2A4A"),
        showlegend=legend, legend=dict(orientation="h", y=-0.18),
    )
    ...
    return fig
```

### 4.2 数值滚动动画（进阶 1）

`st.metric` 没法做动画，所以用 `components.html` 在 iframe 里画卡片，数字用 `setInterval` 从 0 缓动到目标值——`easeOutCubic`，42 帧、每帧 22ms，大约 0.9 秒滚完：

```javascript
var timer = setInterval(function () {
  frame += 1;
  var p = frame / total;
  var v = target * (1 - Math.pow(1 - p, 3));   /* easeOutCubic：先快后慢 */
  if (p >= 1) { v = target; clearInterval(timer); }
  el.textContent = fmt(v);
}, 22);
```

跑马灯和卡片渐入都用纯 CSS `@keyframes` 实现，比 JS 省事，也不会因为 Streamlit 重跑而丢状态。

### 4.3 定时局部刷新（扩展 1）

`@st.fragment(run_every="5s")` 可以让**只有这一个区块**定时重跑，页面其他部分不动——这是做「实时监控面板」最省事的办法：

```python
if f["refresh"] and HAS_FRAGMENT:
    @st.fragment(run_every="%ds" % f["refresh"])
    def live_panel():
        tick = st.session_state.get("tick", 0) + 1
        st.session_state["tick"] = tick
        top = (df_view.groupby("品类")["销售额"].sum() / 10000).sort_values(ascending=False)
        pick = list(top.index)[tick % len(top)]
        ...
    live_panel()
else:
    st.info("把「自动刷新频率」设为 5/10/30 秒，即可开启定时局部重跑")
```

频次做成了侧边栏可选项（关闭 / 5 / 10 / 30 秒），而不是写死——演示时开，平时关，避免无意义的重跑。

### 4.4 点击下钻（进阶 2）

筛选器负责「看哪一部分数据」，下钻负责「从这一部分再钻一层」。两者叠加，但不互相改写：

```python
fig = plot_chart(fig_category_bar(df_view), key="ch_cat", select=True)
label = clicked_label(fig)          # 点空白处返回 None
if label and label != st.session_state.drill_cat:
    st.session_state.drill_cat = label
    st.rerun()
```

`on_select="rerun"` 是 1.35+ 才有的能力，所以代码里用 `inspect.signature` 做了版本探测，老版本自动降级成「只能看不能点」。下钻选中后在页面上显示一个 chip 标签，点 × 取消——这个细节很关键，否则用户会不知道「为什么少了一半数据」。

## 五、验证：让程序自己判对错

「看起来没问题」不能算验收。看板这边写了三组自检：

1. **数据层**：清洗后空值 0 个、订单编号 `nunique == len(df)`（5,060 = 5,060）、维度数量 6 个品类 / 5 个渠道 / 7 个地区 / 24 个月；
2. **对账层**：品类汇总表的销售额合计 == 总销售额 KPI 卡，占比合计 == 100.0%；
3. **渲染层**：用 `streamlit.testing.v1.AppTest` 跑一遍页面，断言 `exception` 数量为 0；再用无头 Edge 渲染全页截图，人工再核一遍排版。

其中第 2 条最能说明问题：如果汇总表和 KPI 卡各自算各自的，早晚会出现「两个数差几千块」的尴尬；现在它们走的是同一个 `df_view`，数字不可能对不上。

## 六、踩过的坑

这部分比结论更有复用价值：

1. **日期解析不能一步到位。** 原始数据里有 `2024/1/5`、`2024.01.05`、`2024-1-5` 三种写法，直接 `to_datetime` 会有一半变成 NaT。正确姿势是先把分隔符统一替换成 `-`，再 `to_datetime(errors="coerce")`，最后统计 NaT 数量对账。
2. **全角空格肉眼看不见。** `"手机数码"` 和 `"手机数码　"`（末尾全角空格）分组时是两个品类，图里会莫名多出一根柱子。清洗时必须 `replace("\u3000", "").strip()`。
3. **大数字会挤爆坐标轴。** 销售额动辄几十万，Y 轴标签变成 `600000` 这种长串，图宽不够就重叠。统一除以 10000 换成「万元」后干净很多。
4. **Streamlit 的 DOM 结构会随版本变。** 想用 CSS 精准改某个组件的样式，`data-testid` 在 1.30 → 1.37 之间改过名字，写死的选择器升级就失效。能用自带参数就别硬改 CSS。
5. **1280px 窄屏下 KPI 卡会截断。** 五张卡一行放不下，数字被裁掉。用 `@media` 在 1280 / 960 / 720 三档降级，窄屏自动变两列。
6. **pip 装不进系统 Python。** 系统里同时有 Anaconda 3.8 和 Python 3.12，`pip install streamlit` 装到了 A 解释器、运行时用的却是 B。最后每个实验工程各自建 `.venv`，问题消失。
7. **GBK 控制台打不出 emoji。** `print("📊")` 在 Windows 默认控制台直接 `UnicodeEncodeError`，加 `PYTHONIOENCODING=utf-8` 或改用 logging 都能绕开。

## 七、小结

做完这个看板，对「数据可视化」的理解变了一点：**图表的难点不在画出来，而在让人相信它画得对。**

同样的数据，柱状图和环形图放一起，读者会下意识比较两者的高度和弧长；如果两者用了不同的口径（一个含退货、一个不含），图本身没有错，但结论错了。所以这次把「统一 `df_view`」和「汇总表对账 KPI 卡」当成硬性约束——宁可少画两个图，也不要出现两套口径。

另外，进阶部分的动效、下钻、预警，本质上都是在回答「然后呢」：看到品类占比之后想看具体商品（下钻），看到月度趋势之后想知道哪个月不正常（预警），看到数字之后想确认它没在骗人（对账）。功能是围绕问题长出来的，而不是反过来。
